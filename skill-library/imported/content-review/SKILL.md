# Content Review

Review any outbound content before it goes public. Catches factual errors, tone drift, brand violations, unsupported claims, and compliance risks. Applies to blog posts, one-pagers, social media drafts, investor updates, landing pages, and documentation.

## When to Use
- Before publishing a blog post or article
- Before sending investor or stakeholder updates
- Before posting to social media or community channels
- When reviewing content generated by another agent (especially Gemini)
- When drafting marketing materials referencing technical claims

## Execution

### 1. Load the content
Read the file or accept pasted content. Identify the content type (blog, one-pager, social, docs, email).

### 2. Factual accuracy audit
For every quantitative claim, technical assertion, or "we have X" statement:
- Verify against the codebase (grep for referenced files, classes, functions)
- Verify against git history if claiming shipped/production status
- Flag any claim that cannot be verified as `UNVERIFIED`
- Flag any claim contradicted by evidence as `INCORRECT`
- Note the evidence source for verified claims

**Zero tolerance for fabricated metrics.** Round numbers, inflated counts, and unverifiable statistics must be caught. Watch for inflated metrics from automated agents.

**Internal infrastructure metrics** (bus message counts, test counts, uptime figures, version numbers cited as production evidence) require the same receipt standard as external research: show the command output (grep/wc/git log) that produced the number. Treat round numbers like "11,000+" or "15,000+" as red flags requiring verification before they appear in any outbound document.

**Standards item numbers** (OWASP ASI-N, NIST SP 800-N, ISO 42001 Art.N, EU AI Act Art.N, SOC 2 CC-N): any document claiming a specific numbered item in an external standard must have that number verified against the live canonical document before READY status is assigned. Flag as NEEDS VERIFICATION if not verifiable from local corpus alone. Do not accept prior research entries as authoritative — fetch the source.

### 3. Tone and brand check
Apply your organization's brand voice (see `[brand-guidelines]` for full reference):
- Concise, direct, technically precise
- Active voice
- No buzzwords: "leverage", "synergize", "cutting-edge", "revolutionary", "game-changing"
- No superlatives without evidence: "best", "only", "first" require citation
- Intellectual confidence without arrogance
- Dry humor acceptable; forced enthusiasm is not

### 4. Compliance and legal scan
- No leaked secrets, internal paths, or credentials
- No unsubstantiated competitive claims ("we're better than X" needs evidence)
- No promises of regulatory compliance (say "addresses" or "maps to", not "compliant with")
- OWASP/NIST/EU AI Act references must cite the correct document and date
- Open source license implications if referencing code

### 5. Audience calibration
- Technical audience: include file paths, class names, test counts
- Business audience: lead with outcomes, defer implementation details
- Mixed audience: layered (executive summary + technical appendix)
- Flag if the content mixes audiences without clear separation

### 6. Structure and readability
- Lead with the strongest claim or insight
- Every section should answer "so what?"
- Tables over prose for comparisons
- No wall-of-text paragraphs (5 lines max)
- Headings should be scannable -- reader should get the gist from headings alone

## Severity Guide
- **HOLD**: Contains incorrect claims, leaked secrets, or legal risk. Do not publish.
- **NEEDS REVISION**: Has unverified claims, tone issues, or structural problems. Fixable.
- **READY**: All claims verified, tone correct, no compliance issues. Ship it.
